# ADR-002. 인제스천에 LangGraph 를 쓰되, 문서당 LLM 루프는 두지 않는다

> **이 문서의 독자**: 6개월 뒤의 나, 그리고 인수인계받을 사람

- 상태: **채택**
- 날짜: 2026-11-25
- 관련: ADR-001(조항 단위 청킹), `src/finrag/ingestion/graph.py`, `src/finrag/ingestion/nodes.py`

---

## 맥락

**무엇이 문제였나.** 2회차까지는 파싱 → 검사 → 청킹을 함수로 따로 불렀다. 문서 49건은 품질이 제각각이다.
어떤 문서는 그대로 읽히고, 어떤 문서는 특정 쪽만 글자가 깨지고, 어떤 문서는 스캔 이미지이고, 어떤 문서는 HWP 라 아예 못 읽는다.
문서마다 **어느 길로 갔고 왜 거기서 멈췄는지**가 남지 않으면, 검색이 틀렸을 때 원인이 파싱인지 검색인지 가를 수 없다.
그리고 실패한 문서가 조용히 빠지면 "정답 청크가 없어서 못 찾은 것"을 "검색이 못한 것"으로 오해하게 된다.

측정된 사실 (학생 환경, 문서 49건):

| 무엇 | 값 | 출처 |
|---|---|---|
| 처리 문서 · 청크 | 49건 · 3,694개 | `data/ingest_report.json` (documents, chunks) |
| 게이트 판정 분포 | pass 40 · reparse 5 · ocr 2 · fail 2 | `data/ingest_report.json` (verdicts) |
| 최종 상태 | done 46 · failed 3 | `data/ingest_report.json` (routes) |
| 사람 검토 큐 3건 | HWP 1 · HWPX 1 (지원하지 않는 형식) · knia_4000 1 (쓸 쪽 없음) | `data/ingest_report.json` (failed) |
| LLM 복구된 문서 | 0건 (키 없음) | `data/ingest_report.json` (llm_repaired) |
| 첫 검색 성능 (Dense) | Recall@5 72.5% · MRR 0.530 | `results/baseline.json` (overall) |

**문서 한 건의 경로 — `knia_4000` (손보협회 공시, 1쪽, 띄어쓰기가 사라진 문서)**

| 항목 | 값 |
|---|---|
| 문서 ID | `knia_4000` |
| 게이트 판정 | `reparse` (재추출 필요 1쪽) |
| 지나간 경로 | classify → parse → gate → reparse → llm_repair → dead_letter |
| 최종 상태 | `failed` (사람 검토 큐) |
| reasons | "재추출 필요 1쪽", "쓸 수 있는 페이지가 없음" |
| warnings | "LLM 키가 없어 복구를 건너뜀" |

판정은 `reparse` 인데 최종 상태는 `failed` 다. 다른 파서로 다시 읽어도 쓸 쪽이 0장이라 `route_after_reparse` 가 `llm_repair` 로 보냈고,
키가 없어 복구를 건너뛰고 이유를 남긴 채 검토 큐로 갔다. **판정(verdicts)과 최종 경로(routes)는 다르다**는 것이 이 문서로 보인다.
게이트 fail 은 2건인데 failed 가 3건인 이유가 이 문서다.

## 대안

| # | 대안 | 장점 | 단점 | 왜 안 골랐나 |
|---|---|---|---|---|
| A | 문서마다 LLM 에게 읽혀서 정리시킨다 | 깨진 글자·표도 그럴듯하게 복원한다. 규칙을 안 짜도 된다 | 문서 49건 × 매 실행마다 API 비용. 수백 쪽 문서는 분 단위 지연. 같은 문서에서 매번 다른 결과. 판정 이유를 설명할 수 없다 | **비용·지연·재현성** 셋 다 잃는다. 게다가 LLM 이 깨진 조항을 지어내면 그게 근거로 인용된다. 약관 RAG 에서 가장 위험한 실패다 |
| B | if 문으로 직접 짠다 (함수 안에서 분기) | 의존성이 없다. 지금 분기 수(4갈래)면 코드도 짧다 | 어느 문서가 어느 길로 갔는지 기록을 직접 만들어야 한다. 같은 파일 재처리 건너뛰기(체크포인트)도 직접 짜야 한다. 분기가 늘수록 중첩 if 가 읽기 어려워진다 | 분기 자체는 쉽지만 **경로 기록과 재실행**을 매번 손으로 구현해야 한다. 4회차부터 이 위에 검색이 얹히는데, 흐름이 코드 속에 숨어 있으면 고치기 어렵다 |
| C | LangGraph 로 노드 8개 + 조건부 엣지. 기본 경로는 파서와 정해 둔 검사 규칙만, LLM 은 쓸 쪽이 0장일 때만 | 문서마다 상태(route, report, warnings)가 남아 리포트가 저절로 나온다. 연결표가 코드에 그대로 보인다. 기본 경로는 결정적이라 매번 같은 결과 | 라이브러리 의존성 하나 추가. 스케줄링·재시도 큐는 해 주지 않는다 | **← 골랐다** |

## 결정

> 인제스천은 LangGraph 그래프(classify → parse → gate → reparse/ocr/llm_repair → chunk/dead_letter)로 처리하고, 기본 경로에는 LLM 을 두지 않는다. LLM 은 다른 파서로 다시 읽어도 쓸 수 있는 쪽이 0장인 문서에만, temperature 0 · 결과 캐시 · `llm_repaired` 표시를 붙여 마지막 수단으로 쓴다.

## 근거 지표

| 지표 | 전 (2회차, 함수 따로 호출) | 후 (3회차 그래프) | 차이 |
|---|---|---|---|
| 경로가 기록된 문서 | 기록 안 함 | 49/49 (경로 합 = 문서 수) | 빠진 문서 없음을 확인 가능 |
| 실패 문서의 이유 기록 | 기록 안 함 | 3/3 (reasons·warnings 있음) | 검토 큐에서 왜 왔는지 바로 앎 |
| 인제스천 중 LLM 호출 | 해당 없음 | 0회 | API 비용 0원 |
| reparse 문서 중 청크를 만든 문서 | 해당 없음 | 4/5 | 나쁜 쪽만 갈아 끼우고 문서는 살림 |

"전" 칸은 2회차에 같은 항목을 측정하지 않았다. 문서마다 LLM 을 썼을 때의 비용·지연은 **측정하지 않았다**(대안 A 는 실행하지 않음).

측정 방법: `data/ingest_report.json` 의 documents · routes · verdicts · failed · llm_repaired 를 집계
재현 명령: `.venv\Scripts\python pipelines\ingest.py` → `.venv\Scripts\python scripts\check_session.py 3`

## 대가

| 잃은 것 | 얼마나 | 받아들일 만한 이유 |
|---|---|---|
| 글자가 깨진 문서의 본문 | 1건 (`knia_4000`, 1쪽) 이 검색에서 빠짐 | 지어낸 본문이 근거로 인용되는 것보다 빠진 채 이유가 남는 편이 안전하다. 검토 큐에 남아 있어 사람이 처리할 수 있다 |
| HWP · HWPX 문서 | 2건이 검색에서 빠짐 | 형식 문제라 LLM 으로도 못 고친다. 변환 도구를 붙이는 것은 별도 결정이다 |
| 의존성 | `langgraph` 패키지 하나 | 상태·분기·경로 기록을 직접 짜는 비용보다 작다 |

## 되돌릴 조건

- [ ] 사람 검토 큐(`failed`)의 문서가 전체의 `10%` 를 넘으면 (지금 3/49 = 6%) → 문서당 LLM 복구 범위를 다시 검토
- [ ] LLM 호출 비용이 문서당 `10원` 아래로 떨어지고, 같은 입력에서 같은 출력을 보장하는 설정이 가능해지면
- [ ] 문서 수가 `500건` 을 넘어 사람 검토 큐를 손으로 처리할 수 없게 되면
- [ ] 스캔·손글씨 문서처럼 파서로 읽히지 않는 문서가 코퍼스의 주류가 되면

되돌리는 비용: `nodes.py` 에서 `llm_repair` 를 부르는 조건 한 곳(`route_after_reparse`)만 바꾸면 된다. 인제스천 재실행 약 6분, 인덱스 재생성은 바뀐 청크만 다시 임베딩.

## 결과

인제스천 49건 · 청크 3,694개 · 검토 큐 3건으로 끝났고, `make check-s03` 은 ADR 작성 전 5/6 이었다. 검색 품질의 변화는 4회차에서 같은 baseline 과 비교한 뒤 채운다.

> **메모 (2026-11-25, 선택 과제 후).** 위 표의 "LLM 복구 0건"은 키 없이 돌린 전체 실행(`data/ingest_report.json`) 기준이다.
> 이후 OpenAI 키(`openai:gpt-5.4-mini`)로 `knia_4000` 한 건만 다시 돌렸다(`pipelines/ingest.py --only knia_4000 --no-checkpoint`).
> 결과는 `data/ingest_report_sample.json` 의 `llm_repaired: ['knia_4000']`, 청크 1개(`meta.llm_repaired: true`)이고, 전체 결과(3,694개 · 검토 큐 3건)는 바꾸지 않았다.
>
> | 프롬프트 | 원문에서 빠진 글자 | 지어낸 글자 | 흩어진 숫자 처리 |
> |---|---|---|---|
> | v1 | 10자 ("천만원", 숫자 "2" 등) | 0 | "3년만기", "1만원"처럼 짐작해서 붙임 |
> | v2 (채택) | 0 | 0 | 원래 순서대로 둠 (띄어쓰기만 복원) |
>
> v2 는 "원문 글자 삭제 금지", "붙을 곳이 확실하지 않으면 옮기지 말 것" 규칙을 더했다. 원문 보존은 지켰지만 깨진 표는 거의 그대로라 읽기 어렵고, `[판독불가]` 표시는 두 버전 모두 0회였다.
> **결정은 바꾸지 않는다.** LLM 은 약관에서 숫자를 짐작해 옮길 수 있다는 것이 v1 에서 실제로 보였고, 이것이 기본 경로에 LLM 을 두지 않는 이유를 뒷받침한다.
> 참고: `Settings` 가 `.env` 의 `OPENAI_API_KEY` 를 환경변수로 넘기지 않아, 실행 시 PowerShell 에서 직접 환경변수로 넣어야 했다.
